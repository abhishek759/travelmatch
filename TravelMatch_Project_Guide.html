What Is TravelMatch?

TravelMatch is a full-stack web platform that helps people find compatible travel companions. It has five core features:

  • Smart Matching — scores users against each other using a weighted algorithm across budget, style, destinations, duration, and accommodation
  • Group Trip Management — create or join trip groups using invite codes
  • Real-Time Chat — AJAX polling fetches new messages every 2 seconds without refreshing
  • Collaborative Itinerary — drag-to-reorder day plans shared across all members
  • Expense Tracking — splits costs equally, exactly, or by percentage; auto-calculates who owes what

Database Models
core/models.py — Every database table as a Python class, and why each field exists.
core/models.py

In Django, you define your database structure in Python — not SQL. Each class is a table. Each class attribute is a column. Django's ORM translates your Python into SQL automatically. When you change a model and run makemigrations, Django figures out what SQL ALTER TABLE statements are needed.

💡
Key concept: ForeignKey A ForeignKey means "this row belongs to one row in another table." For example, GroupMember.group = ForeignKey(TripGroup) means each membership record belongs to one group. on_delete=models.CASCADE means if that group is deleted, all its memberships are deleted too.

Model 1: Profile

Django's built-in User model only stores username, email, and password. Profile extends it with everything TravelMatch needs for matching.

class Profile(models.Model):
    # Links to exactly one User. If the User is deleted, Profile is deleted too.
    user          = models.OneToOneField(User, on_delete=models.CASCADE, related_name="profile")
    bio           = models.TextField(blank=True)
    avatar_url    = models.URLField(blank=True)

    # JSONField stores a Python list in a single DB column, e.g. ["europe", "east_asia"]
    destinations  = models.JSONField(default=list, blank=True)
    travel_months = models.JSONField(default=list, blank=True) # [6, 7, 8] = Jun/Jul/Aug

    # Single-value preferences — stored as short strings
    style         = models.CharField(max_length=20, choices=STYLE_CHOICES, default="mixed")
    budget        = models.CharField(max_length=10, choices=BUDGET_CHOICES, default="mid")
    duration      = models.CharField(max_length=20, choices=DURATION_CHOICES, default="week")
    accommodation = models.CharField(max_length=10, choices=ACCOMMODATION_CHOICES, default="hotel")

    # Flag: has the user completed the onboarding questionnaire?
    onboarding_complete = models.BooleanField(default=False)

    # @property = computed on the fly, not stored in DB
    @property
    def preference_dict(self):
        # Returns a plain dict — used by the matching algorithm
        return { "destinations": self.destinations, "style": self.style,
                  "budget": self.budget, "duration": self.duration,
                  "accommodation": self.accommodation }

Models 8, 9 & 10: Expense, ExpenseAllocation, BalanceLedger

These three work together to track shared costs:

ModelWhat it storesExample
ExpenseThe expense itself — who paid, how much, what forAlice paid $120 for hotel
ExpenseAllocationEach member's individual share of that expenseAlice: $40, Bob: $40, Carol: $40
BalanceLedgerRunning net balance per person (updated incrementally)Alice: +$80, Bob: -$40, Carol: -$40
🔑
Why BalanceLedger exists Without it, to show balances you'd have to sum all expense allocations every time — slow for large groups. Instead, every time an expense is added or deleted, we update the ledger instantly. Balance lookups then take a single fast database query (O(1) instead of O(n)).

How the ledger is updated when Alice pays $120 split equally among 3 people:

# Alice paid $120, split equally 3 ways ($40 each)
# delta = (amount_paid - own_share) for payer, (-own_share) for others

Alice:  delta = (120 - 40) = +80   # Alice is owed $80
Bob:    delta = (0   - 40) = -40   # Bob owes $40
Carol:  delta = (0   - 40) = -40   # Carol owes $40

Matching Algorithm
core/services/matching.py — The mathematical heart of TravelMatch. How compatibility is scored.
core/services/matching.py

This file answers: "How similar are two users' travel preferences?" The answer is a number between 0 and 1, where 1 means perfect match.

The Compatibility Formula Score(A, B) = (budget_sim × 0.35)
               + (destinations_sim × 0.25)
               + (style_sim × 0.20)
               + (duration_sim × 0.12)
               + (accommodation_sim × 0.08)
FeatureWeightMethodLogic
budget35%Ordinal similarityExact = 1.0  |  One tier apart = 0.5  |  Two tiers apart = 0.0
destinations25%Jaccard similarity|intersection| ÷ |union| of their destination sets
style20%CustomExact = 1.0  |  Either is "mixed" = 0.6  |  Different = 0.0
duration12%Ordinal similaritySame as budget — weekend/week/twoweeks/extended are ordered tiers
accommodation8%Exact matchSame preference = 1.0  |  Different = 0.0

Ordinal Similarity

Used for budget and duration — these are ordered scales where "nearby" values are somewhat compatible:

# Budget tiers in order: economy → mid → luxury
BUDGET_TIERS   = ["economy", "mid", "luxury"]
DURATION_TIERS = ["weekend", "week", "twoweeks", "extended"]

def _ordinal_sim(val_a, val_b, tiers):
    dist = abs(tiers.index(val_a) - tiers.index(val_b))
    return 1.0 if dist == 0 else (0.5 if dist == 1 else 0.0)

# Examples:
# economy vs economy → dist=0 → 1.0 (perfect)
# economy vs mid     → dist=1 → 0.5 (partial)
# economy vs luxury  → dist=2 → 0.0 (no match)

Jaccard Similarity (Destinations)

Jaccard measures the overlap between two sets. It's ideal for destinations because two people might both want to visit 3 out of 5 of the same regions.

def _jaccard_sim(set_a, set_b):
    a, b = set(set_a), set(set_b)
    if not a and not b: return 0.0
    return len(a & b) / len(a | b)  # intersection ÷ union

# Example:
# Alice: ["europe", "east_asia", "caribbean"]
# Bob:   ["europe", "east_asia", "africa"]
# intersection = {"europe", "east_asia"} → size 2
# union        = {"europe","east_asia","caribbean","africa"} → size 4
# Jaccard      = 2/4 = 0.50

Worked Example

Alice (adventure, mid, week, hotel, europe+asia) vs Bob (cultural, mid, week, hotel, europe+americas):

budget_sim        = ordinal("mid", "mid")           = 1.00
destinations_sim  = jaccard(["europe","east_asia"],
                            ["europe","south_america"]) = 1/3 = 0.33
style_sim         = style("adventure", "cultural")  = 0.00
duration_sim      = ordinal("week", "week")          = 1.00
accommodation_sim = "hotel" == "hotel"               = 1.00

Score = (1.00×0.35) + (0.33×0.25) + (0.00×0.20) + (1.00×0.12) + (1.00×0.08)
      = 0.35 + 0.083 + 0.00 + 0.12 + 0.08
      = 0.633  →  63.3% compatible

get_ranked_matches()

def get_ranked_matches(current_user, limit=20, threshold=0.0):
    # Step 1: find users already acted on (liked or passed)
    acted_ids = set(MatchAction.objects.filter(actor=current_user)
                               .values_list("target_id", flat=True))
    acted_ids.add(current_user.pk)  # exclude self too

    # Step 2: get candidates who completed onboarding
    candidates = User.objects.exclude(pk__in=acted_ids)\
                             .filter(profile__onboarding_complete=True)\
                             .select_related("profile")

    # Step 3: score each candidate
    results = []
    for user in candidates:
        score = compute_compatibility(my_pref, user.profile.preference_dict)
        if score >= threshold:
            results.append((user, score))

    # Step 4: sort descending by score, return top N
    results.sort(key=lambda x: x[1], reverse=True)
    return results[:limit]

Settlement Algorithm
core/services/settlement.py — Minimize bank transfers to settle group debts.
core/services/settlement.py

After a trip, some people are owed money and some owe money. The naive solution is for everyone to pay everyone — which could be many transfers. This algorithm finds the minimum number of transfers to settle everything.

🧮
Mathematical guarantee For a group of n members, this algorithm always produces at most n - 1 transfers, no matter how many expenses were added.

The Algorithm

def compute_settlement(balances: dict) -> list:
    """
    Input:  {user_id: net_balance}
            positive balance = others owe this user
            negative balance = this user owes others
    Output: [{"from_user": id, "to_user": id, "amount": float}]
    """

    # Split into creditors (owed money) and debtors (owe money)
    creditors = [[uid,  bal] for uid, bal in balances.items() if bal >  EPSILON]
    debtors   = [[uid, -bal] for uid, bal in balances.items() if bal < -EPSILON]

    # Sort both by amount (largest first)
    creditors.sort(key=lambda x: x[1], reverse=True)
    debtors.sort(key=lambda x: x[1], reverse=True)

    transfers = []
    ci, di = 0, 0

    while ci < len(creditors) and di < len(debtors):
        cred_id, credit = creditors[ci]
        debt_id, debt   = debtors[di]

        # Transfer the smaller of what the creditor is owed vs what the debtor owes
        amount = min(credit, debt)
        transfers.append({"from_user": debt_id, "to_user": cred_id, "amount": round(amount, 2)})

        # Reduce both sides
        creditors[ci][1] -= amount
        debtors[di][1]   -= amount

        # If either reaches zero, move to the next person
        if creditors[ci][1] < EPSILON: ci += 1
        if debtors[di][1]   < EPSILON: di += 1

    return transfers

Step-by-Step Example

4 people went on a trip. After all expenses:

PersonNet BalanceMeaning
Alice+$120Others owe Alice $120
Bob+$30Others owe Bob $30
Carol-$80Carol owes $80
Dave-$70Dave owes $70
Step 1 Sort creditors: Alice($120), Bob($30)
          Sort debtors: Carol($80), Dave($70)

Step 2 Match Carol($80) → Alice($120): transfer $80
          Carol settled. Alice now needs $40 more.

Step 3 Match Dave($70) → Alice($40): transfer $40
          Alice settled. Dave still owes $30.

Step 4 Match Dave($30) → Bob($30): transfer $30
          Both settled. Done!

Result: 3 transfers instead of potentially 12 (4×3).

The Convenience Wrapper

def compute_group_settlement(group):
    # Read balances from BalanceLedger for this group
    ledger   = BalanceLedger.objects.filter(group=group).select_related("user")
    balances = {entry.user_id: float(entry.net_balance) for entry in ledger}

    # Run the algorithm (returns user IDs)
    raw = compute_settlement(balances)

    # Look up actual User objects so templates can show usernames
    user_map = {u.pk: u for u in User.objects.filter(pk__in=balances.keys())}
    return [{"from_user": user_map[t["from_user"]],
              "to_user": user_map[t["to_user"]],
              "amount": t["amount"]} for t in raw]

CSRF tokens in AJAX requests Every POST request in Django must include a CSRF token to prevent cross-site request forgery attacks. In the templates, we include a hidden form <form id="csrf-form">{% csrf_token %}</form> and JavaScript reads the token from it: document.querySelector('#csrf-form [name=csrfmiddlewaretoken]').value. This is appended to every AJAX POST.
Chapter 10
How Everything Connects
End-to-end flows showing how all the files work together for each major feature.

Flow 1: User Signs Up

1. Browser visits /accounts/signup/
→ urls.py routes to signup_view() in views.py

2. GET request: view creates empty SignUpForm
→ renders auth/signup.html with the form

3. User fills form and submits (POST)
→ SignUpForm validates: username unique? passwords match? email valid?

4. If valid: User created with hashed password
→ Profile created (blank) for that User
→ User logged in automatically
→ Redirect to /onboarding/

5. Onboarding form shown, user fills preferences
→ Profile.destinations, travel_months, style, budget, etc. saved
→ onboarding_complete = True
→ Redirect to /matches/

Flow 2: Compatibility Matching

1. User visits /matches/
→ match_feed() called

2. services/matching.py: get_ranked_matches(user)
→ Queries all users with onboarding_complete=True
→ Excludes already-acted-on users (via MatchAction table)

3. For each candidate: compute_compatibility(my_prefs, their_prefs)
→ Runs _ordinal_sim, _jaccard_sim, _style_sim
→ Returns weighted sum score (0.0–1.0)

4. Sort by score descending, take top 20
→ Multiply by 100 (for "%" display)
→ Render matches/match_feed.html

5. User clicks "Like" on a card
→ JavaScript POSTs to /matches/<id>/action/
→ match_action() saves MatchAction(actor, target, "like", score)
→ Returns JSON {ok: true}
→ JavaScript fades out and removes the card

Flow 3: Real-Time Chat

1. User opens group_detail.html (Chat tab is default)
→ Django renders all existing messages server-side

2. JavaScript starts polling loop (every 2 seconds):
    fetch("/groups/<pk>/chat/messages/?since=<lastId>")
→ chat_messages() view returns only NEW messages
→ JavaScript renders them and updates lastId cursor

3. User types message + presses Enter
→ JavaScript POSTs to /groups/<pk>/chat/send/
→ chat_send() creates Message in DB
→ Returns the message as JSON
→ JavaScript immediately renders it in the chat box
→ Other users' polling picks it up within 2 seconds

Flow 4: Adding an Expense

1. User clicks "Add Expense" → modal opens with ExpenseForm

2. User fills in: description, amount $120, currency USD, split=equal
→ JavaScript submits form via fetch() to /groups/<pk>/expenses/add/

3. expense_create() view:
    - Gets all 3 group member IDs
    - Calculates equal share: $120 ÷ 3 = $40 each

4. Inside transaction.atomic() (all-or-nothing):
    - Creates Expense record ($120)
    - Creates 3 ExpenseAllocation rows ($40 each)
    - Updates BalanceLedger for each member:
      payer: net_balance += (120 - 40) = +$80
      others: net_balance += (0 - 40) = -$40 each

5. Returns {ok: true} → page reloads to show updated list

Flow 5: Settlement Plan

1. Expenses tab loads → group_detail() reads BalanceLedger
→ Calls compute_group_settlement(group)

2. settlement.py reads net balances from BalanceLedger
→ Splits into creditors (+) and debtors (-)
→ Greedy algorithm matches largest creditor with largest debtor
→ Produces minimum transfer list

3. Template renders: "Carol pays Alice $80" etc.
→ Color coded: red = payer, green = receiver
